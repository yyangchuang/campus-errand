> 创建时间：2026-10-08

---

## 一、产品一句话

> 同学 A 发单 → 平台认证的跑腿员 B 接单 → 送达 → 结算

---

## 二、两类角色 + 权限层级

| 角色 | 谁能当 | 能干什么 |
|---|---|---|
| **普通用户（发单者）** | 所有同学，微信授权即可 | 只能发任务 + 看自己的单 |
| **跑腿员（接单者）** | **平台指定/审核通过**的少数人 | 能接任务 + 看自己接的单 |
| **管理员** | 运营负责人 | 管理跑腿员名单（添加 / 移除）|

**核心规则**：
- 一个账号**只能是其中一种角色**，不双身份
- 普通用户**没有任何接单入口**，看不到待接单
- 跑腿员账号由管理员**手动添加白名单**（MVP 阶段）
- 管理员可以在后台加人，也可以暂时封某人的接单权限

## 三、TabBar 两套（按角色显示不同菜单）

### 普通用户 TabBar（3 个）

| 位置 | 菜单名 | 功能 |
|---|---|---|
| ① | **发任务** | 填写快递信息、地址、跑腿费 → 发布 |
| ② | **我的单** | 我发过的所有订单 + 状态 + 详情 |
| ③ | **我的** | 头像 / 昵称 / 退出 |

### 跑腿员 TabBar（3 个）

| 位置 | 菜单名 | 功能 |
|---|---|---|
| ① | **待接单** | 平台派给我的新任务列表 |
| ② | **我的单** | 我接过的所有订单（已完成 + 进行中） |
| ③ | **我的** | 头像 / 昵称 / 工号 / 退出 |

**同一位置的"我的单"，发单者看"我发的"，跑腿者看"我接的"，互不干扰。**

## 四、完整业务流程

### 发单端（普通用户）

```
[发任务]                         [我的单]                       [我的]
┌──────────┐                ┌──────────────┐                ┌──────────┐
│ 驿站      │                │ 订单列表      │                │ 资料      │
│ 地址      │ ──发布订单──▶ │ 点进详情      │ ──签收/取消──▶ │ 退出登录  │
│ 跑腿费    │                │ 状态流转      │                │          │
└──────────┘                └──────────────┘                └──────────┘
                                 │
                                 │ 联系跑腿员（拨号）
                                 ▼
```

### 接单端（跑腿员）

```
[待接单]                         [我的单]                       [我的]
┌──────────┐                ┌──────────────┐                ┌──────────┐
│ 新任务列表 │ ──接单──▶     │ 我接过的单    │ ──联系发单──▶  │ 工号/状态 │
│ 点进去    │                │ 点"已送达"    │                │ 退出登录  │
└──────────┘                └──────────────┘                └──────────┘
```

## 六、订单状态机（5 状态）

```
发布 ─────────────────────────────┐
                                  ▼
                              待接单 ── 跑腿员点"接单" ──▶ 跑腿中
                                  ▲                         │
                                  │                    跑腿员点"已送达"
                                  │                         ▼
发单者点"取消" ─────────────────▶ 已取消                 已送达
                                  ▲                         │
                                  │                    发单者点"签收"
                                  │                         ▼
                                  └──────────────────── 已完成
```

### 状态 × 角色 操作

| 当前状态 | 发单者 | 跑腿员 |
|---|---|---|
| 待接单 | 取消订单 | 立即接单 |
| 跑腿中 | 联系跑腿员 | 点"已取件"/"已送达" |
| 已送达 | 点"确认签收" / 联系跑腿员 | 联系发单者 / 等签收 |
| 已完成 | —— | —— |
| 已取消 | —— | —— |

## 九、技术实现要点（权限管控）

### 用户表设计

```sql
users {
  id              // 唯一 ID
  openid          // 微信 openid
  nickname        // 昵称
  avatar          // 头像
  school          // 学校
  role            // 'user' | 'runner' | 'admin'
  runner_no       // 跑腿员工号（仅 runner 有）
  created_at
}
```

### 关键判断逻辑

```javascript
// 登录后拿角色
const role = user.role;

if (role === 'user') {
  // TabBar: [发任务, 我的单, 我的]
} else if (role === 'runner') {
  // TabBar: [待接单, 我的单, 我的]
} else if (role === 'admin') {
  // 管理员后台（MVP 可先不做）
}
```

### 添加跑腿员（MVP 方案）

| 方案 | 操作 | 推荐 |
|---|---|---|
| A. 管理员后台手动改 | 运营端直接把某人 role 改成 runner | MVP 最快 |
| B. 跑腿员申请 + 审核 | 跑腿员登录后点"申请接单权限"，管理员审核通过 | 后期升级 |
| C. 邀请码机制 | 管理员生成邀请码，跑腿员注册时填入 | 中间方案 |

**建议 MVP 用 A：数据库手动改 role 字段，最快。**
